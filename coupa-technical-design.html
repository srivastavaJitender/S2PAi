Tool registry — 12 tools Claude calls autonomously
Claude reads each tool's description to decide which to call and when. No fixed order — Claude chooses based on context.
Fetch  Context gathering
get_invoice(invoice_id)
Full invoice — header, lines, tax, WHT
Always called first
get_vendor_master(vendor_id)
Vendor config — WHT codes, tax setup
When WHT codes are unfamiliar
get_vendor_history(vendor_id)
Past errors from agent memory — patterns, attempt counts
Always called early — shapes validation strategy
check_duplicate(vendor_id, invoice_number, amount, date)
Check for similar existing invoice from same vendor
Claude decides — unusual amount or vendor history
Validate  Compliance checks
validate_tax(invoice_id)
4 rules across all invoice lines — rate, amount, code
Almost always — Claude may skip for known-clean vendors
validate_wht(invoice_id)
WHT codes on invoice vs vendor master allowed codes
Almost always called
check_po_tolerance(invoice_id, po_id)
Invoice amount vs PO value — must be within 5% tolerance
Only when a PO is referenced on the invoice
Act  Coupa actions
post_comment(invoice_id, comment)
Claude writes the comment text itself — specific, structured, contextual. No templates.
After every decision
submit_invoice(invoice_id)
Submit for approval, clear AP hold code
Only on full pass
set_on_hold(invoice_id)
Hold invoice, update AP hold code
Fixable errors — AP can correct
escalate(invoice_id, reason, urgency, escalate_to)
Hold + email AP manager. For recurring issues (3+), large amounts, or systemic errors AP alone cannot fix.
Claude decides when pattern warrants escalation
Learn  Memory — what makes this truly agentic
store_reflection(invoice_id, vendor_id, action_taken, reasoning, pattern_detected, rule_suggestion)
Writes to vendor_patterns.json — Claude's long-term memory. Next time this vendor's invoice arrives, Claude reads this history first and adapts its validation strategy. This is how the agent gets smarter over time.
Always called last — never skipped
Example: Claude's reasoning chain for a 3rd-offence invoice
# EY Israel — INV-2024-0461 — 3rd WHT failure in 30 days # Iteration 1: Claude starts with context "I'll fetch the invoice and check vendor history before validating." → get_invoice("461") → get_vendor_history("vendor_123") # Returns: 2 prior WHT failures, same code IL_Z9_99, both held # Iteration 2: Claude adapts — validates but anticipates escalation "EY Israel failed WHT twice before. Same code. Third occurrence likely. I'll validate but I'm already leaning toward escalation." → validate_tax("461") # Returns: PASSED → validate_wht("461") # Returns: FAILED — IL_Z9_99 again # Iteration 3: Claude synthesises and acts differently than RPA would "Third occurrence. AP held it twice, vendor master unchanged. This is systemic. Holding again won't fix it. ESCALATE." → post_comment("461", "[Claude's own contextual comment — 3rd occurrence, escalated]") → escalate("461", reason="3rd WHT failure — vendor master issue", urgency="high") → store_reflection("461", pattern="Recurring IL_Z9_99 — needs vendor master fix") # RPA would have held it for the 3rd time. Claude escalated. # Total: 7 tool calls across 3 iterations.

Rule 1aTax rate vs master rate
Blocks
Checks the tax rate on the invoice line matches the rate configured on the tax code in Coupa master data.
Line rate
20%
Master (IL_VAT_17)
17%
Result
FAIL
if line_tax_rate != line_tax_rate_expected: findings.append(f"Line {"{"}line_num{"}"}: rate {"{"}line_tax_rate{"}"}% ≠ master {"{"}line_tax_rate_expected{"}"}%")
Rule 1bZero-rate code, non-zero amount
Blocks
Catches zero-rate tax codes (EXEMPT, ZERO) where a non-zero tax amount was entered.
if line_tax_rate_expected == 0 and line_tax_amount > 0: findings.append(f"Line {"{"}line_num{"}"}: '{"{"}line_tax_code{"}"}' is 0% but amount {"{"}line_tax_amount{"}"} entered")
Rule 1cTax amount vs master rate
Blocks
Verifies tax amount is mathematically consistent with master rate × line total. Tolerance ±0.05.
expected = round(line_total * line_tax_rate_expected / 100, 2) if abs(line_tax_amount - expected) > 0.05: findings.append(f"Line {"{"}line_num{"}"}: {"{"}line_tax_amount{"}"} ≠ expected {"{"}expected{"}"}")
Rule 2Tax amount vs line rate
Blocks
Checks amount consistency with the rate actually entered on the line. Catches rounding errors and manual overrides.
expected = round(line_total * line_tax_rate / 100, 2) if abs(line_tax_amount - expected) > 0.05: findings.append(f"{"{"}line_tax_rate{"}"}% of {"{"}line_total{"}"} = {"{"}expected{"}"}, got {"{"}line_tax_amount{"}"}")

How validators are invoked in v3.0
# Validators called via tool handlers — not hardcoded in agent.py async def handle_validate_tax(invoice_id: str) -> str: invoice = await coupa_client.get_invoice(invoice_id) lines = await coupa_client.get_invoice_lines(invoice_id) result = await tax_validator.validate(invoice, lines) return json.dumps(result.dict()) # string returned to Claude # Claude calls both tools — handlers run them in parallel internally # Result: Claude sees "Tax: PASSED" and "WHT: FAILED — IL_Z9_99" # Claude then reasons about what those results mean in context
